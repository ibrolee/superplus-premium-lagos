# Reception registration and returning-member fee waivers (proposal and implementation gates)

Owner decision 2026-09-21: new members registered by reception require **no management approval before registration**. Management performs financial reconciliation **after registration**, not an approval of the member's identity or membership creation. A separate one-time coupon can waive **only** the registration fee for an independently identified existing gym member creating their first online profile. Do not confuse these flows.

## New member at the desk (Option A)
1. Reception checks the member directory first. If an old member already exists, do not create a duplicate or charge a second registration fee.
2. Reception enters name, verified contact, official plan, price, and payment method. Only mark collection as received when the receptionist personally counted cash or actually checked the gym's POS/bank credit. A customer screenshot is not sufficient. An idempotent server endpoint checks staff role, duplicate contacts, current prices and fees.
3. One server-side transaction creates the member profile and an active provisional membership immediately, with staff attribution and an accompanying **pending** payment. No independent manager is needed for registration. Pending payments are **not confirmed revenue**; the provisional membership is shown clearly in staff screens.
4. A *different* manager later independently reconciles the collection against the actual bank/POS/cash deposit. On reconciliation, mark payment successful and membership paid. On dispute, mark payment failed, cancel the provisional membership and deny scanner entry; preserve the member profile and immutable audit trail. Never allow self-reconciliation or a second use of the same verification reference.
5. Legacy pending new-member requests remain available for historical review and must not be silently converted or duplicated.

## One-time coupon for a returning member creating an online profile
- This is **not a generic promotional coupon**. Reception finds the existing member first, checks documented prior membership or legitimate historical import, and verifies identity in person. If no record exists, an administrator must resolve the historical identity; do not let an anonymous checkout claim prior membership.
- Issue a long, cryptographically random, single-use code bound to that verified member ID and their stored email/phone, with expiry, issuer and audit record. Store only the hash of the code, never its plaintext; display once to give to that member. Allow revocation and replacement if lost.
- On the public Join page the member enters the coupon, the checkout server validates it against the member identity, then reduces **registration fee only** to ₦0. Keep the plan price unchanged. Show original fee, waived amount and payable total before Paystack.
- The server must compute all amounts: **never** trust a client-provided discount. The Paystack initializer writes member-bound coupon ID, registration-fee waiver and expected amount into trusted transaction metadata. The verifier independently re-checks Paystack's SUCCESS status, currency, amount, coupon eligibility, member identity and one-time redemption. Redemption, member linking, paid membership and successful payment must be committed atomically and idempotently, with the coupon consumed only on confirmed payment. Cancelled/failed payments must not consume the coupon.
- Use verified contact/account ownership before linking a historic member to an online login; coupon possession alone must not allow account takeover. Avoid creating duplicate profiles or a second joining fee. Existing member renewal without coupon continues using the original plan price and server-authoritative process.
- The existing `initialize-public-payment` and `verify-public-payment` functions currently hardcode full registration and verification amounts, respectively. Adding just a Join-page coupon field would be dangerous: the verifier would reject the reduced amount or a weaker client-side path could undercharge. Implement and test both sides together in a separate release gate.

## Current staging / release gates
- Source-controlled preview branch only. No production Supabase migration, Edge deployment, environment flag, production Vercel merge or production payment mutation without explicit owner approval.
- The new registration page is feature-gated (`VITE_RECEPTION_INSTANT_ENABLED=true` only after backend and scanner are ready). A preview with flag off shows the UX but cannot create records.
- Complete scanner dispute protection, dedicated read-only reconciliation queue, manager review UI and verified backend/unit/e2e role matrix before enabling. Review cashier, manager, duplicate, idempotent retries, simultaneous submissions, reference collision, failed reconciliation, Paystack isolation, audited finance totals and QR validity.
- Coupon issuance and public checkout changes remain **a separately scoped implementation stage**, not live functionality. Do not advertise codes as working before checkout initialization AND verification are implemented and tested.
